How it works

One loop, three parties

  1. DraftThe agent turns a plain request into clauses with a definition of done. Unverifiable asks are listed, not dropped.
  2. ApproveA person approves the sensitive clauses. Each approval is bound to a hash of the exact terms.
  3. ExecuteThe agent runs against sandboxed billing and memory providers, with idempotency keys and bounded retries.
  4. VerifyPure functions over provider observations. They never read the agent's claims.
  5. RepairFixes derived from the verifier's reasons, approved by a person, then re-verified.
  6. ReceiptObligations, approvals, verdict history and evidence digests, with an integrity check that catches edits.

What is new here

Approval gates are the floor. Outcome verification is the point.

Common in agent apps What Trust Contract Studio adds
The agent can't approve its own actions The agent's report is constrained to an executor-independent verifier's verdicts
“200 OK” or a commit receipt as proof The promised outcome is read back from provider state: a 200 OK that changed nothing is FAILED
Success or failure UNKNOWN is a first-class answer for timeouts, stale replicas and stores with no read interface
“Deleted” because the delete API said so Residual memories found by lineage closure across replicas, and disguised copies found by a pgvector similarity search
Guardrails for the app's own agent Any MCP agent (Claude Code, Cursor, another company's bot) is held to the same contract, without the approval tool
An audit log of what ran A human-approved repair loop to VERIFIED, and a receipt with the full verdict history

Built on Agent-Native

One action, two callers

Every capability is one defineAction(). The UI calls it through action hooks and the in-app agent gets it as a tool, so “Draft contract” on screen and “draft it for me” in chat run the same code. Integration tests run the same action objects as both callers.

The agent knows which contract is on screen through the framework's navigation state and opens the canvas for you. decide-approval is not a tool the agent has, and wiping the workspace pauses on the framework's needsApproval.

The same actions are served over the framework's MCP endpoint, so an outside agent can draft, execute and repair under a contract. Approval, reset and the tamper drill are not in its catalog. The memory index runs on PostgreSQL + pgvector (Neon in production).

Honest limits

What it does not claim

  • All providers and data are synthetic sandboxes. The faults live in the providers, never in the verifier.
  • Verification covers only the stores registered in the workspace, not erasure anywhere else.
  • No claim of legal compliance, exactly-once execution in external systems, or immutability. The receipt says what is not proven.
