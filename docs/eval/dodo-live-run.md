# Live provider check: Dodo Payments (test mode)

Generated by `pnpm demo:dodo` (`scripts/dodo-live-check.ts`) on 2026-11-09. This is the one place where the verifier judges a **real provider** instead of the sandbox. Raw output: [`dodo-live-run.json`](dodo-live-run.json) and [`dodo-live-run-clean.json`](dodo-live-run-clean.json).

**Setup.**

- The provider is Dodo Payments in **test mode** (`test.dodopayments.com`): simulated card payments and refunds.
- Each run starts a fresh $100/month test subscription, paid with a saved test card (4242…). No browser is involved.
- The contract has two clauses: cancel that subscription, and refund **$50.00** of its first payment.
- The adapter, [`server/providers/dodo.ts`](../../server/providers/dodo.ts), reads Dodo with GET requests only. It returns the same observation types as the sandbox, and the **unchanged** `verifyObligation()` judges them.
- The executor's claims are recorded for comparison only. They are never inputs to the verifier.

## What this shows, and what it does not

- The same pure verifier that the 512-combination evaluation checks against an oracle also reads a real provider's state. It catches a real over-refund that the executor reported as "Done".
- **Scope.**
  - This covers only the cancellation and refund clauses, and only in test mode.
  - Erasure and memory purges still run on the sandbox stores, with the memory index on a real pgvector engine. Dodo has no endpoint for deleting a customer.
  - The Studio UI still runs on the sandbox. This check runs from the command line.
- **Repairs.** Refunds at a real provider cannot be voided. The repair for an over-refund is therefore a person's decision: recover the money or accept the loss. It is not something the agent can do automatically.
- **Refund state.** A refund that is still `pending` or `review` at Dodo makes the observation unusable, so the verifier answers UNKNOWN instead of guessing. Refunds that `failed` do not count as money returned.
