# LLM judge vs verifier

Generated by `pnpm eval:llm-judge` (`scripts/eval/llm-judge-eval.ts`). Judge model: **gpt-6-luna** through the Builder.io gateway, temperature 0.

**Question.** Teams often check an agent by asking another model whether the work is done. Would that have caught the broken promises?

**Setup.**

- 64 fault combinations: one in every 8 of the 512 used by the [outcome evaluation](outcome-eval.md). Each runs the demo request through draft, human approval and execution.
- **The judge** sees what a reviewer of the agent sees: the request, each promise with its definition of done, every tool call with the provider's response, and the agent's final report. It answers KEPT, BROKEN or CANNOT_TELL per promise.
- **The verifier** reads provider state through the observation layer and never sees the agent's report.
- **Ground truth** for both comes from the same independent oracle, which reads the sandbox tables directly.

## Results (256 promises, 80 actually broken)

|                                             | LLM judge on the log, forced to decide | LLM judge on the log, may abstain | LLM judge on the log **plus the same provider observations** | Verifier, first look | Verifier after up to 2 fresh observations |
| ------------------------------------------- | -------------------------------------- | --------------------------------- | ------------------------------------------------------------ | -------------------- | ----------------------------------------- |
| **Broken promises accepted as kept**        | **26**                                 | **0**                             | **0**                                                        | **0**                | **0**                                     |
| Broken promises caught                      | 51                                     | 1                                 | 32                                                           | 40                   | 80                                        |
| Broken promises left undecided              | —                                      | 78                                | 44                                                           | 40                   | 0                                         |
| **Kept promises wrongly flagged as broken** | **131**                                | **1**                             | **8**                                                        | **0**                | **0**                                     |
| Kept promises left undecided                | —                                      | 167                               | 108                                                          | 88                   | 0                                         |

Out of 80 broken and 176 kept promises. The agent said "Done" on all 80 broken ones. Judge calls that failed: 4 run(s).

**This is not an even contest, and that is the point.**

- Judged on the log alone, the LLM sees what most "is the agent done?" checks see. It either abstains on everything or, forced to decide, errs in both directions.
- Given the same observations as the verifier, the LLM is a fair comparison of reasoning over evidence.
- The verifier is deterministic code with the definition of done written down. It costs no model call, gives the same answer every time, and says UNKNOWN, with the reason, when a provider cannot be read. A fresh observation then resolves the UNKNOWNs caused by the injected timeouts and stale replicas.

## Limits

- **A sample.** These are 64 combinations, one judge model, one prompt, and one run per combination.
- **Same faults.** The sandbox and its faults are ours, as in the outcome evaluation.
- **Different inputs, by design.** The judge only has the log. That is the point being measured: a log can say "200 OK" and "Done" while the provider's state says otherwise.
